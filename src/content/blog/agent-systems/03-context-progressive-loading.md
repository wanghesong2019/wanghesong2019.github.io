> 这是「AI Agent 系统底层」系列的第 3 篇。前两篇我讲了 agent 是台"新计算机"、harness 才是真正的产品。这一篇，钻进 harness 最烧钱、也最容易被忽略的一层——上下文（context）——看它到底是怎么被浪费的，以及该怎么做。

先说一个我反复撞见的场景。

你给 agent 装了 20 个 MCP server，写了 500 行 CLAUDE.md，让它干个活，它得先读十几个文件才动手。跑起来之后，它越来越慢、越来越笨、账单越来越长。你的第一反应是什么？

"这模型不行，换个更强的。"

停。我要泼的冷水是：**问题大概率不在模型，在你塞进上下文窗口的那几万 token 里。** 课程里有一组数据，我觉得值得每一个做 agent 的人刻在脑门上：

> 同一个模型，只改 harness 的上下文管理，**SWE-bench Verified 从 43 题做对 72 题**——准确率几乎翻倍，模型一个字没换。

所以这篇要回答的是：**agent 的上下文窗口里到底塞了什么？为什么"塞得越多"反而"做得越差"？以及怎么把那些被浪费的 token 省回来。**

---

## 上下文是有限的，而且是"租金"

先立一个认知：**上下文是租来的，不是买断的。**

课程里把这件事拆成三宗罪，一句话点破每一宗的本质：

- **成本**：每一步推理都会**重新发送整个窗口**。你窗口里那 5 万 token，不是付一次钱，是每 turn 都付一次。常驻的东西越多，每 turn 的账单越厚。
- **延迟**：prompt 越大，prefill 和 decode 越慢。窗口臃肿 = 每一轮都更慢，agent loop 转得越慢。
- **注意力**：模型对窗口的"记忆"会随窗口变长而衰减，**中间的内容尤其容易被漏掉**。这就是那篇著名的《Lost in the Middle》——论文里给 20 篇文档排位置，答案放在第 1 位和第 20 位的准确率，比放在第 5 到 10 位高出一大截。

一句话收束：**上下文不是"越大越好"，它是一个每次 turn 都要重新付钱的有限资源。** 你把它当无限内存用，就是在烧钱的同时让 agent 变笨。

---

## 解剖上下文窗口：你的 token 都花哪了

课程给了一张很有用的"单个 agent turn 的 token 预算表"（示意值），我抄在这里：

| 层 | 大概 token | 性质 |
|---|---|---|
| System prompt（角色、规则、输出契约） | ~2K | 静态，常驻 |
| Tool definitions（工具 schema） | ~6K | 常驻，**用不用都占着** |
| Retrieved context（文件、搜索命中、文档） | ~25K | 按需拉入 |
| Message history（历史 turn + 原始工具输出） | ~8K | **涨得最快** |
| Project environment（scratchpad、笔记） | ~80K 且继续涨 | 主动读回 |

<p align="center"><img src="/images/d3-context.png" alt="上下文窗口 token 预算" width="45%" /></p>
<p align="center"><small>▲ 上下文窗口五层 token 预算：红=常驻税，绿=按需，黄=涨最快</small></p>

看到问题了吗？**"常驻"的那两层（系统提示 + 工具定义），加一起就 8K 了，而且每一笔都是"税"——无论这次 turn 用不用得到，它们都躺在窗口里，每 turn 都重付一次钱。**

而真正该按需加载的东西（检索上下文），反而混在常驻和膨胀的历史里，一起把窗口撑大。

课程在这里有句很扎心的话：**"Every schema costs tokens, used or not."（每一个工具 schema 都要花 token，不管用不用得到。）**

---

## 常驻税是怎么榨干你的：一个具体的账

光说抽象没意思，我算一笔课里的实账。

假设你给 agent 挂了 60 个工具（20 个 MCP server，每个 3 个工具，很常见）。这 60 个工具的 schema 全部常驻，吃掉 **42,000 token**。

而一次普通的任务，实际用到的工具，3 个顶天了。

也就是说，**你每 turn 都在为另外 57 个压根没碰的工具付 token 钱。** 这不是优化空间，这是纯浪费。

课程给出的解法叫 **offloading（卸载）**：别让 60 个 schema 常驻，而是放一个**索引**在窗口里，等模型真的要用某个工具时，再按需把它的 schema 拉进来。结果：

> 60 个 schema 常驻 = 42,000 token → **索引 + 3 个 schema = 3,100 token**。**93% 更小，60 个工具全部可达。**

同样的思路用在"往上下文里塞 DOM"这种场景：原始 DOM 48,000 token 直接灌进去，模型照样答对；但你只要在门口做个"工具输出塑形"，只留价格和标题，**900 token 就够了——98% 更小，答案一模一样。**

记住这两组数字，它们是这篇文章最硬的证据：**常驻税不是小钱，是几万 token 量级的大头。**

## 解法：三级渐进加载

上面说的 offloading，落到具体实现，就是 Anthropic 在 Agent Skills 里正式提出的**三级渐进加载（progressive disclosure）**。

一个 skill 是一个文件夹，里面是 `SKILL.md`（描述 + 流程）+ 可选的 `references/` + `scripts/`。它被分三层加载：

1. **第一层：名字 + 描述**。agent 启动时，把所有 skill 的 `name` 和 `description` 预载进系统提示。这层只占一点点 token，但足够让模型判断"这个 skill 跟当前任务有关吗"。
2. **第二层：SKILL.md 正文**。只有当模型判断某个 skill 相关时，才把它的完整 `SKILL.md` 读进上下文。
3. **第三层：捆绑文件**。正文里引用到的 `references/`、`scripts/`，等真正走到那一步再打开。

本质就是一句话：**描述常驻（发现）、正文按需（加载）、文件最后（展开）。** 把"税"压到最低，把"能发现"的能力保住。

这和我上一篇（第2篇）拆 Claude Code 时提到的 skill/MCP 三级加载是同一件事——那一篇我埋了个伏笔说"名称常驻、正文按需、资源最后再开"，这一篇就是把这个机制的**为什么**讲透：因为上下文是租来的，常驻就是每 turn 都交房租。

## 更完整的框架：管上下文的四种手段

三级加载是 offloading 的一种，但课程给的框架更全。管理上下文有四种手段，从"无损"到"有损"依次是：

- **Admission（准入）**：在门口拦。查询要窄（取字段不取整篇文档）、工具输出要塑形（留摘要去原始负载）、必要时才截断、把原始 payload 丢给 subagent 隔离。
- **Offloading（卸载）**：不常驻，按需取。渐进式工具定义、工具搜索、返回句柄按需加载、把计划写到磁盘、持久记忆只留小索引。**三级渐进加载就属于这一类。**
- **Transformation（变换）**：选择性丢历史。去重（只留每个对象最新状态）、观察掩码（老于 N 步的工具结果剥掉）、滑窗（只留最近几轮 + 头部）。课里的账：96,000 token → 24,000（**75% 更小，且没有做任何总结，纯去重**）。
- **Compaction（压缩）**：最后的手段，用 LLM 总结。滚动摘要、全量摘要。它**有损、不可逆**，所以课程特意加了警告：要预留输出空间、保住系统前缀、压缩后重新注入关键事实。

这四种手段按"预防 → 有损"排成一条光谱。你该做的，是**尽量在前面解决（准入、卸载），别一上来就上压缩**——压缩是丢信息的，前面的手段不丢。

## 三个反直觉点

**反直觉点一：换模型之前，先换 harness。**

这是全篇的题眼，我再说一遍那组数据：SWE-bench Verified，同一个模型，基础 harness 做对 43 题，改进 harness（压缩旧工具输出 + 保留最近观察 + 检测卡住并干预）做对 **72 题**。课程原话：**"Some apparent 'model failures' are actually context- and control-loop failures."（很多看似"模型不行"的失败，其实是上下文和控制回路的失败。）**

所以下次你想"上更强的模型"之前，先问一句：我是不是在用模型的钱，去填 harness 的坑？

**反直觉点二：上下文不是越大越好，中间还会"失忆"。**

直觉上"多给点信息总没错"，但《Lost in the Middle》和上下文注意力衰减的实验都指向反面：窗口越长，模型对中间内容的 recall 越差，还可能被无关信息带偏。课程甚至列了"上下文失败的 5 种方式"——中毒、分心、混淆、冲突、漂移。**加信息是有代价的，不是免费的。**

**反直觉点三：工具 schema 是你看不见的常驻税。**

大多数人优化 agent 时盯着 prompt 抠字眼，却对窗口里那 6K 工具定义、20 个 MCP 的 schema 熟视无睹。而这一笔，恰恰是"不用也付钱"的纯税。课程那句"tool design is context design"（工具设计就是上下文设计）点透了：**你每加一个工具，不只是在加能力，还在给每个 turn 加税。**

## 放进系列脉络

这一篇拆的是六层栈第 2 层（harness）里的"上下文管理"。但它和后面 Part II 的 serving 是直接连着的：

| 你在上下文里做的操作 | 落到的系统问题 | 后续篇目 |
|---|---|---|
| 每 turn 重发整窗 | prefill 成本 / 前缀缓存 | 第15篇 |
| 常驻 schema 占位 | 前缀缓存的常驻段 | 第15篇 |
| 窗口膨胀 → 压缩 | KV-cache 管理 | 第15篇 |
| 三级加载省 token | $ / 成功任务的成本 | 第9篇 |

**harness 里的每一个"省 token"的决定，最终都会变成 serving 层真金白银的成本差。** 这也是为什么这门课把"agent 设计"和"LLM serving"串成一条线——它们本来就是一回事的两头。

---

## 一个可带走的结论

> **别急着换更强的模型。先把你塞进上下文窗口的几万 token 里，"常驻却不常用"的那部分改成按需加载——同一个模型，光是这一条就能让准确率翻倍、成本腰斩。上下文是租来的，常驻税是你自己在给自己加租。**
